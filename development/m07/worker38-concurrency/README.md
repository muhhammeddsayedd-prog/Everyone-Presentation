## Planned actual cases; not yet executed

1. A normal authenticated caller executes the real specs submit RPC and holds
   its successful transaction open. The pause backend executes the exact
   production Repeatable Read prefix. An independent observer must see it wait
   for the caller's config read lock through pg_locks/pg_blocking_pids. No
   snapshot result has returned. Roll back the caller: the pause backend's first
   full snapshot sees zero work, checks all counters and preservation, and
   executes all five real pause UPDATE blocks. A new intake can wait behind the
   still-held pause locks; after pause commit it must return only the genuine
   DEPENDENCY_UNAVAILABLE denial. That cold caller may wait at a business-table
   lock before reaching config, and no config-only wait is claimed for it.
2. In a rollback-only transaction while paused, seed one failed generic retry
   and two deliberately conservative presentation/export lifecycle rows. The
   exact lifecycle SQL must report1+2 despite disabled flags. The real generic
   retry RPC must queue the job and outbox. Roll back every retry fixture byte
   and require the complete paused snapshot to match again. The two unlinked
   presentation/export rows prove conservative counting, not their retry
   eligibility, saved-version lineage or processing.
3. Restore the five flags and the entire owned baseline. A second real specs
   intake now commits while pause waits. The pause backend's first snapshot
   must see that exact new job and queued/outbox work. Executing the exact
   precondition comparison must fail with WORKER38_INTAKE_DRIFT_REFUSED before
   any pause UPDATE. All config flags must remain enabled.

The raw sessions run their name/OID/marker/system-ID guard in autocommit BEFORE
the application transaction. They do not use ctx.sql()'s BEGIN wrapper for the
pause: doing so could establish a snapshot too early. SQL lock timeout remains
the production5 seconds; observation is bounded to2.5 seconds. All raw backends
have unique owned application names, recorded PID/start/user identity and
bounded output/time. Failure cleanup may cancel/terminate only those exact
owned identities. Backend absence is checked before disposable database drop.

Multi-session visibility requires commits. No enclosing outer rollback is
claimed. Retry fixtures and rejected phases roll back; required flag/intake
commits are confined to the disposable database and removed by exact owned
database cleanup. Original29 business data, full Auth/Storage/catalogue, profile,
settings and global-role identities/memberships must still match exactly. A
normal child return alone never supplies acceptance.
