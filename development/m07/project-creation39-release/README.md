# Project39 canonical release preparation

This new normal-Supabase-CLI controller is disabled for apply. It never invokes
an old release main/claim, extracts CLI credentials, changes transport retries,
or performs cloud work during import/tests. Root owns source review, arming,
inspection, dispatch and reconciliation. Current task authorization is retained.

It binds exact migration bytes, sequential32 SQL assertions, independent-session
same/different-key races, the compatible e494 Ready deployment and the protected
canonical38 application snapshot. Backup bytes are verified privately without
parsing or publishing their business content. Backup is separate from restore
acceptance and excludes managed Auth and Storage object bytes.

The metadata-only collector is the existing frozen full catalogue33 expansion.
The 143-field local39 delta is checked in full, including before values. All other
metadata remains hashed and exact. Full raw old catalogues and OIDs are also
retained, normalizing only the named new object closure, new-role ACL entries,
separately pinned project_dto body, physical statistics and the two FK-parent
trigger-presence flags. Old triggers remain covered individually. Complete direct
grants/ownership for the new role across all schemas are checked separately.
An optional managed bootstrap grant to postgres from supabase_admin is admitted
only with its exact locally observed flags; absence is the sole alternative.

The snapshot retains all74 existing business table hashes plus trace rows,
OAuth configuration hashes, English/Reviewed/Ready/protected-M02 state, full
processing configuration and conservative zero-work counters. Only project39's
new role/schema ACL entries are removed from the existing OAuth envelope; the
complete new-role footprint remains independently required. CLI role17603's
expiry is normalized only under the existing exact role/expiry safety predicate.

Inspect obtains two equal current38 snapshots and writes one protected plan.
Apply requires the armed source, unchanged evidence/backup/source pins and a
fresh equal snapshot, then exclusively creates one permanent dispatch claim.
The transaction locks history and all old business tables, rechecks the full
preimage, applies original39 admission/functional SQL, appends only its history
row and verifies the complete permitted postimage before COMMIT. A nonce marker
after COMMIT and two independent equal readbacks are required for a pass.
Unknown outcomes retain their claim; readback cannot invent a normal return.

Normal commands use only pinned Supabase CLI 2.122.0, the linked canonical target,
protected SQL files and the existing bounded reader/environment. There is no
automatic dispatch retry, reset, seed, provider call, new identity or cloud
business-data write. Data changed since the historical snapshot is not asserted
to be included in it; actual apply preserves its own freshly captured preimage.
