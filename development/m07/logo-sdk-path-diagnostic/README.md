# Logo SDK path diagnostic

Source and synthetic-HTTP diagnosis only, 2026-11-03. No live request, upload,
completion, cancellation, permission change or product fix was performed.

The installed `@supabase/supabase-js` and `@supabase/storage-js` are both 2.118.0.
The test resolves their actual Main installation and imports the actual production
central client, logo adapter and central studio. Fetch and RPC responses are
synthetic; every fetch rejects an unexpected destination.

## Results

- `download(key, {}, parameters).asStream()` makes one GET to
  `/storage/v1/object/<bucket>/<key>`. It does not call `info()`.
- `info(key)` is a separate explicit GET to `/storage/v1/object/info/<bucket>/<key>`.
- The actual logo adapter and complete central studio routing have the same single
  object GET, including when Storage returns wire400/body404. That response becomes
  `UPLOAD_INCOMPLETE` with the four closed download diagnostic fields; no verifier,
  finalize or cancel runs after it. A successful synthetic GET reaches verification.
- Worker specs use an independently mapped capability URL with
  `/object/authenticated/`; they do not use this SDK download builder. Worker and
  acting-user logo requests also have different authority contexts.

The retained hosted policy catalogue has `eps.logo_storage_read_allowed` checking
only `storage.allow_only_operation('object.get_authenticated')`. Its ordinary
own-open-upload path does not admit `object.get_authenticated_info`.
`eps_logo_read` calls that helper. The restrictive `eps_logo_read_guard` has info
alternatives for separate presentation/export/guest capability paths, which do
not add ordinary own-upload info access. This is a concrete operation distinction,
not proof that it caused this failure.

Official Storage source maps both legacy and explicit authenticated object GETs
to `GET_AUTH_OBJECT`; both info paths map to the separate `GET_AUTH_OBJECT_INFO`.
The optional `storage.` prefix is normalized by `allow_only_operation`; complete
operation names remain different. Adding an `authenticated` path segment alone
therefore is not an established repair.

## Evidence boundary and next discriminant

The observed live `/object/info/...` event is not generated by the checked logo
completion path in these tests. SDK preflight, gateway delegation and attribution
must not be conflated. The next useful evidence is the original app/gateway event
correlation for the completion request and the Storage event: method/path,
server operation name, safe upstream/client provenance and closed status/code.
No authorization header, cookie, token, signed URL or raw error body is needed.

If that correlation establishes a trusted backend info subrequest, its distinct
operation explains why the ordinary logo predicate would refuse it, subject to
the hosted helper/version evidence. Until then, no RLS, key or client-route change
is justified. Later correct object metadata does not prove original physical GET
or acting-user RLS access.
