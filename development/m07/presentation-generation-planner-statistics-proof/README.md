# Original graph planner statistics experiment

This is disabled source preparation. No database, Docker, ANALYZE, generation,
provider or hosted action was performed to prepare it. Importing the entry is
inert and its literal execution flag is false.

The question is whether normal planner statistics materially affect the existing
production function graph in the established synthetic large fixture. Neither
missing statistics nor repeated authorization call sites prove a bottleneck.
The current seven-target trace returned queued in 7,901.047 ms, while the earlier
uninstrumented c024 first call timed out. That is not performance acceptance.

## Two bounded arms

Root may review and separately admit one `control` controller and one `analyzed`
controller. Each uses a new independent network-none PG17 restore38 to exact39
and40, the same frozen fixture/fit preparation and one fresh-backend MCP-large
generation call. Each arm has its own private/evidence/once namespace. There is
no automatic second call, retry, warm measurement or continuation on an unknown
ANALYZE result. A normal application 57014 is retained as an observed failure;
a queued response is only this diagnostic's result, rolled back before closure.

Both arms leave helper4107, canonical DATA/review/GEN/raw, Englishc68, scalar5eb
and public validator9fe unchanged. The callback removes every product-function
installation, including no-op CREATE OR REPLACE, and all prosrc exclusions.
All eight full pg_proc identities and source hashes are checked before and after;
the full application row/pg_proc baseline is compared after rollback. Existing
configuration restoration, original29 data/catalogue/global roles, shared lock,
resource identity and cleanup behavior are inherited unchanged. No old entry,
controller, claim or candidate-specific freshCarry evidence is executed/replayed.

The control arm requests no ANALYZE. The treatment runs exactly one ordinary
ANALYZE statement over the closed 18-table list, as the existing owned bootstrap
superuser, after explicit database/system/history/role checks. The write is in
BEGIN/COMMIT with statement_timeout and lock_timeout both eight seconds. Failure
or unknown return stops before generation. ANALYZE intentionally changes owned
planner metadata such as pg_class estimates and pg_statistic; those changes are
not business writes or product-function changes and are not hidden with a broad
catalogue mask. They disappear when that owned cluster is removed. Original
target data and catalogue equality remains exact.

Before/after setup and after the call, the closed metadata query records actual
observation times, estimates/pages, analyze timestamps/counters and live/modification
estimates. It does not read statistical value distributions, source rows, claims,
tokens or transcript text. Counters/estimates are not exact row counts; reporting
lag and possible autovacuum activity remain visible, not disabled or masked.
If control autoanalyze counters/timestamps change between observations, that is
an interpretation confound; it does not authorize a retry or disabling it.

Both fresh measured senders record their inherited settings, then explicitly use
the same observed canonical session profile: `jit=off`, `plan_cache_mode=auto`,
`default_statistics_target=100`. The effective profile is read back before the
one application call. Treatment uses the same statistics target for ANALYZE.
This does not assert that earlier owned measurements used that profile, and
does not change production settings, role attributes, function costs or timeouts.

## Existing evidence and limits

The normal read-only canonical receipt is
`tracking/evidence/m07/completion-release/canonical-planner-stats-e2813947-7ccb-4f96-820b-6b156f3e8653.json`,
SHA256 `8df6f004e2cc99e92fa43962dcc6523c93324910548f9836ddf927094a37a27d`.
It observed JIT off, automatic plan cache mode and statistics target100; several
relevant tables had reltuples=-1 and no recorded analyze. It proves that observed
metadata only. Production JIT cannot be blamed when that observation says off.

Independent restores avoid calling a warmed second application backend an ANALYZE
effect. Fresh backend is not cold machine/shared/OS cache. Arm order, host load,
UUIDs and statistics sampling remain uncontrolled differences; one pair cannot
establish causation or a speedup. No cross-run business hash equality is claimed.
No EXPLAIN ANALYZE, function tracking, cache reset, autoanalyze disabling, index
hint, timeout increase, RLS/auth/session/clock cache or production change is added.

If later needed, a separately reviewed exact nested-query plan can distinguish
row-estimate/scan/subplan behavior from live authorization cost. A top-level
EXPLAIN of a PL/pgSQL function is not its nested-query plan. Plans and raw private
data would remain private; only closed numeric/node summaries could be public.
The full8/16, lock/RLS/authority/race, signed OAuth, hosted, PDF and production
acceptance gates remain separate. No seven-target performance result is carried.

PostgreSQL explains that ANALYZE supplies planner statistics after bulk changes
and that EXPLAIN ANALYZE executes its statement:
[EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html).
JIT decisions depend on estimated plan cost, not measured milliseconds:
[JIT decisions](https://www.postgresql.org/docs/17/jit-decision.html).
