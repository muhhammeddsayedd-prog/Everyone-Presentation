# Controlled Vercel worker pilot

This is an implemented local source package, not a hosted-worker acceptance receipt. No provider resource, VCR push, deployment, private configuration upload, canonical job or paid-provider call was performed by its author. The owner coordinates those operations separately.

The web and worker use separate Vercel projects. The web receives no worker database login, OpenAI key, n8n dispatch secrets or worker OIDC identity. The worker project runs one serial Daemon in `dub1` with `2Gi` requested memory. Its existing central PostgreSQL outbox/leases/callback fences and n8n work orders remain authoritative. No HTTP worker adaptation, Vercel Queue or Workflow replaces them. Daemons currently run only in Vercel's production deployment environment; this isolated deployment remains a controlled pilot, not production release acceptance.

Every native operation uses a fresh credential-free Sandbox microVM: document extraction, video preparation/probing/frames, PDF raster, review fit, canonical PDF render/validation, and guest PDF render/validation. OpenAI, n8n, database access, Storage authorization and output publication stay in the daemon. `EPS_NATIVE_TRANSPORT` defaults to the existing local Docker path outside Vercel. Vercel admission requires the explicit Sandbox mode and the image-baked manifest; a missing/invalid cloud selector cannot fall back to a daemon child.

The Sandbox has an exact VCR digest, one vCPU / 2048MB, `networkPolicy: 'deny-all'`, `persistent: false`, no exposed ports, drives, source checkout, snapshots or forwarded environment credentials. The image contains only trusted source/tools/public fonts and logos. Sandbox ignores image ENTRYPOINT/CMD, so the parent invokes one fixed absolute launcher with an allowlisted task. The image's root control user handles private SDK files and the supervisor. Untrusted parsing/rendering runs as UID/GID1000, empty supplementary groups, no capabilities, no new privileges, hard CPU/file-size/FD/core/process limits and deadlines. The supervisor requires a root-only mode0700 512MiB `/eps-work` tmpfs and a mode1777 384MiB `/tmp` tmpfs. Unsupported kernel/mount/user behavior fails closed. Sandbox VM limits supply the overall memory/vCPU ceiling; this is not a claim that per-process RSS has been separately measured.

Payload/result files are mode0600 in the root-only work directory, with a size/SHA256 receipt. Native children receive only inherited file descriptors and bounded `/tmp`; they cannot replace the root-owned protocol paths. Raw documents, media, transcripts, PDF bytes and scoped guest-export video links never go through provider command stdout/stderr. The existing guest export grant necessarily appears in its private artifact task payload/PDF; no database/provider/management/OIDC credential enters the VM. Error/public logs contain fixed codes and the generated cleanup identity only.

The transport records an attempted name before create, reconciles unknown create/stop/delete outcomes through exact name/run/source/image/session/configuration, never resumes a VM, and requires removal plus successful empty-list and exact-name GET404 observations. Unconfirmed ownership/cleanup aborts polling and holds the daemon paused until owner shutdown or pilot expiry; it cannot automatically restart into more paid work. Startup refuses any outstanding `eps-native-` object tagged with this transport owner, without adopting/removing it. The owner must reconcile that exact resource before restart. Normal task failures still use the existing durable job retry policy; the transport does not retry native work or paid providers.

The owner explicitly chose **keep running until stopped**. Both web and worker therefore use `EPS_PILOT_OWNER_CONTROLLED=true` with absent/empty `EPS_PILOT_EXPIRES_AT`; a nonempty timestamp in that mode is rejected to prevent contradictory settings. There is no hidden automatic pilot deadline in this mode. If the flag is false/unset, a future canonical UTC expiry is mandatory and aborts worker polling/in-flight work at that deadline with a separate bounded cleanup budget. Invalid flags fail closed. Disabling the web alone does not stop the worker; the owner must stop the dedicated worker deployment/replica as well.

## Build and deployment contract

Use the sparse context emitter, not the repository as a Docker context. It includes package/lock manifests, worker and required package source, registered template versions, six registered fonts with licenses and two public logos. It refuses links and excludes dotenv, `.local`, `.git`, uploads, private fixtures, development and tracking evidence. It creates a new owned directory and never deletes existing resources.

1. Run `node tools/worker-hosting-build.mjs stage`. Preserve its generated run/context/source hash. The emitted root `Dockerfile.native-sandbox` and `Dockerfile.daemon` are exact copies of reviewed sources. Build the native image `linux/amd64` with that context and no build secrets or deployment environment. The owner pushes it to the worker project's VCR and waits for its Sandbox image state to be Ready.
2. Run `node tools/worker-hosting-build.mjs manifest <run> <team/project/native@sha256:digest>`. This adds the exact native manifest to that existing context and reports its SHA256. It does not contact Vercel. Sandbox uses the three-component VCR reference, without a URL scheme/registry hostname. Existing job configuration keeps the `sha256:digest` image identity; the adapter maps only that exact manifest identity to the full VCR image reference.
3. Build/push the daemon image from the same context after adding that manifest. Run `node tools/worker-hosting-build.mjs emit <run> <team/project/daemon.worker@sha256:digest>`. This writes a daemon-only Build Output API tree under that run's `deployment/.vercel/output`: no static files, Functions or HTTP services. The owner links/deploys that isolated output to the dedicated worker project. Missing daemon descriptors on later deployment would stop previous instances; preserve the complete descriptor.
4. Supply private values only as worker runtime variables, never image/build args. The owner uses the existing narrow PG configuration, OpenAI configuration, four separate n8n dispatch URLs/secrets and public Storage configuration. The hosted entry projects only the exact allowlist and denies management/service-role/ambient database credentials. Required public fields are `VERCEL=1`, platform production environment/OIDC token-file path, `NODE_ENV=production`, `EPS_RELEASE_MODE=controlled_pilot`, `EPS_NATIVE_TRANSPORT=vercel_sandbox`, `EPS_NATIVE_MANIFEST_SHA256`, `EPS_PILOT_OWNER_CONTROLLED=true` with blank/absent expiry (the owner-selected mode), and all existing worker feature flags enabled. The three native image IDs are derived from the baked manifest. No personal Vercel API token belongs in the worker.

Do not rebuild from another source graph while reusing an old native image manifest. Both images include the same complete sorted file/hash seal and startup verifies its contents against the pinned manifest. The runtime package pins `@vercel/sandbox=3.9.1`, `@vercel/oidc=4.0.5` and production `tsx=4.23.15`; the Sandbox package's own exact OIDC4.0.0 dependency also supports the Daemon token file. The narrow central runtime is now an explicit worker dependency. The existing Node24 digest, FFmpeg/Poppler package versions and Playwright1.64.1 are pinned; freeze the built image digest after the OS/browser dependency build.

## Required empirical pilot proof

Before privileged polling is enabled, the owner must prove custom-image readiness, Daemon OIDC/token-file refresh, actual image/control UID, deny-all DNS/IP egress, private file modes, source seal, tmpfs/capability/NNP/process/resource restrictions, metadata-only logs, bounded corrupt/cancel/timeout handling and exact VM/session/snapshot absence. Use synthetic files only for that boundary rehearsal. Native source tests and injected SDK tests do not prove these provider/kernel properties. If tmpfs mounting or image USER behavior is unavailable, keep the worker off and revise the isolation design; there is no unsandboxed fallback.

Then prove ordinary authenticated core jobs through the hosted web, real n8n, worker, OpenAI and private Storage, including restart/unknown-ACK/lease/callback behavior. Verify hosted OAuth/MCP after core. The owner configures their own Claude client. Actual full-size/representative video, performance/endurance, provider cost and production release acceptance remain separate evidence. The earlier local synthetic workload and recovery exercises are unchanged and do not supply hosted credit.

## Official sources checked

- [Daemons](https://vercel.com/docs/daemons), [configuration](https://vercel.com/docs/daemons/config-reference), [limits](https://vercel.com/docs/daemons/limits) and [Build Output API](https://vercel.com/docs/build-output-api/daemons): continuous outbound workers, explicit replicas/regions/resources, graceful termination, production-only beta and daemon-only image descriptors.
- [Sandbox SDK](https://vercel.com/docs/sandbox/sdk-reference) and [custom images](https://vercel.com/docs/sandbox/concepts/images): create/runCommand/file streams/lifecycle, VCR digest images, explicit deny-all/nonpersistent settings; image ENTRYPOINT/CMD do not run. Default persistence and default allow-all are explicitly overridden.
- [Functions container runtime](https://vercel.com/docs/functions/runtimes/container) and [Services](https://vercel.com/docs/services): request-driven alternatives; continuous pollers belong in Daemons. A request timeout/background lifetime is not a substitute for the durable worker loop.
